01 — Background

MRP asks "what, how many, when." MRP II asks what it takes to actually make it happen.

MRP

Material Requirements Planning. Answers three questions: which components are needed, how many, and by when.

MRP II

Manufacturing Resource Planning II. Everything MRP does, plus machine and labour capacity, supplier constraints, scheduling, cost, and feedback from the shop floor.

This project builds an MRP II-lite prototype: a simulated furniture factory where independent agents negotiate for materials, suppliers, and machine time — then replan when something breaks.

02 — The idea

One master scheduler, replaced by many small negotiations.

Instead of one system deciding everything, each production order asks independent resource agents — inventory, suppliers, machines — for offers, accepts the best valid combination, and renegotiates only the affected work when a commitment fails.

  • Two orders compete for the same plywood and CNC machine time.
  • Each resource agent offers what it can actually deliver.
  • A machine failure or supplier delay triggers a targeted replan — not a restart.
03 — 22 July 2026

Day 1 had two halves.

Part 1

MRP II fundamentals, explained from the ground up — what it is and why it goes beyond basic MRP.

Part 2

Project architecture — the design work so far: agent responsibilities, negotiation protocol, technology direction.

A worked example illustrated the negotiation idea: 5 production items, each needing a different sequence of steps, moving across 5 production lines, handed off from one line's agent to the next.

04 — The demo

The 5 lines were coordinated through a central hub.

Every line reported to, and took direction from, one central point. Useful for illustrating handoffs — but structurally, this is one component making the decisions.

05 — Feedback

The brief calls for decentralized. The hub read as neutral, not approved.

Sir's core requirement is that no single component should own all the planning decisions. The hub wasn't rejected outright — but it wasn't approved either. It's an open item.

Three existing systems came up for comparison, all of them centralized in the same way the demo hub was:

  • Zoho — a single cloud ERP suite; production planning, inventory, and scheduling all run through one unified platform.
  • Sugar (SugarCRM) — primarily a customer/sales CRM; it connects to ERP systems but isn't itself a manufacturing-planning tool.
  • OpenERP — an open-source ERP suite, renamed Odoo in 2014; modular, but still one system owning the planning logic.
06 — Scope boundary

Not every domain fits a negotiating agent.

Finance was raised as the example: negotiation there happens with external parties — banks, investors, regulatory requirements — not between internal resources, so it can't be modelled as an internal negotiating agent the way inventory, suppliers, or machine time can.

Already consistent

This matches a boundary the project had already set for itself: general ledger, invoicing, and payroll are already excluded from the first version. The comment confirms that boundary rather than introducing a new one.

07 — Data and models

Kaggle first. Synthesize if nothing fits.

  • Look for a suitable dataset on Kaggle first.
  • If nothing suitable exists, synthesize the data instead.
  • Models get trained on that data; those trained models are used by the AI agents.
  • A live simulation of the factory scenario was also discussed for the demonstration.
Open item

The project's existing rule keeps BOM, inventory, capacity, and scoring decisions in plain deterministic code, with models limited to explaining decisions or parsing input. Whether trained models feed in as predictive inputs (a demand or reliability estimate) or are meant to shape the negotiation outcome itself needs to be settled against that rule.

08 — The distinction

What was demoed vs. what's actually planned.

One hub, direct line to every agent. The hub decides; agents execute.

Each agent owns its own state and offers. The plan emerges from scored, accepted proposals — not from one component's decision.

09 — Technology

Mesa, SPADE, and PADE are out. Gemini, the AI SDK, and A2A are in.

Dropped, and why
  • Mesa — an agent-based simulation framework, built to model behaviour in-process, not to pass messages between independently running agents.
  • SPADE — Python, so it would sit alongside the TypeScript dashboard as a second language with its own integration risk; its optional LLM extension was also still in beta.
  • PADE — same second-language issue as SPADE, plus its public docs were written for an older version than the current codebase.
Current plan
  • Gemini — explains decisions and parses draft input. Never plans.
  • Vercel AI SDK — TypeScript toolkit for the LLM-facing parts.
  • A2A protocol — agent-to-agent messaging, in place of SPADE/XMPP. Unlike SPADE, it's a vendor-neutral open standard (Linux Foundation-governed), not one research project's framework.

One language end to end. Material needs, inventory, capacity, and offer scoring stay plain, deterministic code — the model never makes a manufacturing decision.

10 — Next

Before the full negotiation build: one small agent, working end to end.

The next concrete step is a demo agent built on Vercel's Eve framework — a chat interface with a few callable tools — to show the technology stack actually running before the full multi-agent negotiation system is built out.

Open items

  • Revisit Zoho / Sugar / Odoo if the project is expected to be positioned against them specifically.
  • Clarify whether trained models feed the agents as predictive inputs, or are meant to shape the negotiation outcome itself.
  • Confirm the Kaggle-first, synthesize-if-needed dataset approach against the actual scenario data required.
